Turning a Stack Exchange XML dump into analytics tables

A data pipeline that reads 191 MB of raw forum archive and produces clean, queryable tables — running entirely on a laptop, with no cloud account. This report explains what it is, what works, and what is left.

01

What this project actually is

Stack Exchange — the network that includes Stack Overflow — publishes its entire public content as a free archive. One of its sites is ai.stackexchange.com, a question-and-answer forum about artificial intelligence. Its archive is a folder of XML files: one for posts, one for users, one for comments, and so on.

XML is a text format that stores data as nested tags. It is fine for shipping data around, but you cannot ask it questions. There is no way to say "which tags are most popular?" or "what is the average reputation of people who answer questions?" to a 49 MB text file.

This project builds the machinery that turns those files into tables — the rows-and-columns structure that databases understand and that anyone can query with SQL. It does that in deliberate stages, tests each stage, and schedules the whole thing to run as one job.

Why bother, if you could just load the file?

Because the interesting part is not the answer — it is the machinery. The patterns here (staged transformation, explicit schemas, automated tests, scheduled runs, written-down decisions) are what data engineering teams actually build. The dataset is small enough to run on a laptop and large enough that the patterns are not pretend. The project says this about itself, plainly, rather than claiming to handle "big data".

02

The vocabulary, defined

Data engineering has a dense jargon. Every term below appears later in this report, so here they all are in one place. Skim it now, come back to it when a word bites.

Data lakehouse
A place to store data that combines two older ideas: a data lake (dump raw files anywhere, cheap and flexible) and a data warehouse (strict tables you can query fast). A lakehouse keeps files on cheap storage but adds enough structure that they behave like real database tables.
Medallion architecture bronze / silver / gold
The convention this project follows for organising a lakehouse into three layers, named after medals to signal increasing refinement. Bronze is a faithful copy of the raw source. Silver is cleaned and typed. Gold is the finished, business-ready output. The value is that each stage has one job, so a bug has one place to live.
Schema
The declared shape of a table: which columns exist and what type each one is (whole number, text, timestamp). Declaring it up front means the pipeline fails loudly when the source changes, instead of silently guessing.
Apache Spark
An engine for processing data in parallel across many machines. It is heavy machinery, normally used for datasets far larger than this one. Here it is used for exactly one job — reading the XML — because that is the job nothing else in the stack can do.
Delta Lake "a Delta table"
A file format that makes a folder of data files behave like a proper database table — with a transaction log, so a half-finished write never leaves the table in a broken state. This is the format bronze is written in.
dbt data build tool
A tool where each transformation is just a SELECT query in a file. dbt works out the order to run them in, tests the results, and generates documentation. It cannot read raw files — it only transforms tables that already exist. That limitation is the reason Spark is in this project at all.
DuckDB
A database that runs inside your program as a single file, with no server to install or log into. It is what actually executes the SQL here — the reason the whole project runs on a laptop with no cloud account.
Apache Airflow and a "DAG"
A scheduler: it runs jobs in the right order, retries the ones that fail, and shows you what happened. The plan it follows is called a DAG — directed acyclic graph, which is a formal way of saying "a set of steps with arrows between them and no loops."
Cosmos
A plugin that connects Airflow to dbt. Without it, all of dbt is one box in the scheduler — it either worked or it didn't. With it, every individual dbt model becomes its own step, so a failure names the exact model that broke.
CI continuous integration
A robot that runs the tests automatically every time code changes, on a clean machine that shares none of your local setup. If it passes there, it genuinely passes.
ADR architecture decision record
A short written note recording a decision, the reasoning behind it, and what it costs. It answers "why on earth is it done this way?" for whoever reads the code in six months — often the same person who wrote it.
Grain
What one row of a table represents. "One row per post" is a grain. It matters because a bug that quietly changes the grain — say, to two rows per post — inflates every count computed from that table, without anything looking broken.
Idempotent
Running it twice gives the same result as running it once. A pipeline that doubles its data when you retry it is worse than one that simply fails, because nothing alerts you.
Fixture
A tiny sample of real data, saved permanently so tests can run against it in seconds. This project uses five real rows each from the posts and users files — real ones, because they carry the awkward cases that hand-written examples tidy away.

The one decision that explains the whole layout

Spark handles ingestion. dbt handles everything downstream.

Parsing XML is the single job dbt cannot do — dbt only transforms tables that already exist, it cannot read a file. So Spark earns its place at bronze and nowhere else. The moment the data is a table, the work becomes SQL, and dbt provides tests, dependency ordering, and documentation for free. Rebuilding those in Spark would mean rebuilding dbt, badly.

Every other structural choice in the project follows from that one boundary.

What the finished tables contain

Four tables come out the far end. The two silver ones are cleaned-up versions of the raw input; the two gold ones answer actual questions.

Layer Table What it holds Rows
Bronze bronze.posts Every post, exactly as the archive has it. No cleaning at all — this is the untouched copy you compare against when something looks wrong. 26,764
Bronze bronze.users Every user account, likewise untouched. 71,811
Silver stg_posts Posts, cleaned: column names tidied, the pipe-separated tag string split into a proper list, and the numeric post-type code replaced with a readable label ("Question", "Answer"). 26,764
Silver stg_users Users, cleaned. Blank text fields become genuine nulls, so "we have no location for this person" is distinguishable from "their location is an empty string". 71,811
Gold marts_top_tags The most-used tags, ranked by how many posts carry them. 100
Gold marts_posts_users Every post joined to the person who wrote it — one wide table so an analyst never has to work out the join themselves. 26,764

That last row count is not a coincidence, and it is the single most useful number in the project. marts_posts_users must have exactly as many rows as bronze.posts, because its grain is one row per post. Any other number means the join went wrong — and a join going wrong is the kind of bug that inflates every statistic downstream while looking perfectly healthy.

05

The bug that best explains the whole approach

This project began as a set of exploratory notebooks — informal scratch files written while figuring the data out. Converting them into a real pipeline meant reading them carefully, and one of them contained a genuinely instructive defect.

Each post records the ID number of its author. To attach author details, you join the posts table to the users table on that ID. A left join means: keep every post, and attach user details where a match exists; where no match exists, leave those columns empty. That is the right choice, because a post whose author deleted their account is still a post.

On the real data, that column comes out as:

author_statusMeaningPosts
resolvedThe post names an author, and we found them.26,307
anonymousThe post names no author at all.457
unresolvedThe post names an author we have no record of.0

The second defect in the same notebook was quieter: it assumed each user appears only once, without ever checking. If a user ID appeared twice, the join would silently produce two rows for every post that person wrote — inflating every count computed from the table. The fix is a one-line test asserting that user IDs are unique. It has never failed, which is exactly what a good guardrail looks like.

06

Three more bugs, and the pattern they share

Each of these was found during this work, and each is written up as an ADR — a permanent note explaining the decision. What unites them is the failure mode: nothing crashed. Row counts looked right, no job reported an error, and the data was wrong anyway.

Every timestamp was three hours early

The archive stores times with no timezone attached; they are UTC by convention. Spark assumed they were in the timezone of whatever computer was running it, and shifted all of them. Nothing failed. It surfaced only when the data was read back through a second engine, where the offset had to be stated explicitly.

The deeper problem was not accuracy but reproducibility: the same input produced different output depending on who ran it. Now pinned to UTC, and pinned by a test. ADR 0001

A setting that does nothing

The XML reader takes two options naming which tags to read. It turns out one of them is ignored entirely on read — only the other actually selects rows. An earlier notebook had it set wrong, copy-pasted from a different file, and worked anyway.

Worth knowing because getting the other one wrong returns zero rows rather than raising an error — a job that writes nothing and reports success. Now covered by a test.

A database that deleted itself

Cosmos runs dbt from a temporary folder. Every file path in the project was written relative to the project folder, so under the scheduler they all pointed into that temporary space. dbt would build every table into a scratch database which was then deleted when the task ended.

A completely green pipeline run, producing nothing. Fixed by anchoring paths to the project root rather than to wherever the program happens to be running. ADR 0003

Files that lied

Three files in the repo described things that did not exist: a config naming a CSV that was never there, a README listing files that had been deleted, and a Dockerfile that could not have built. All three were committed, all three looked plausible, and nothing read them — so nothing could report the drift.

The rule adopted in response: an artifact must be exercised by something automated, or it gets deleted. Five empty placeholder files were removed under it during this work. ADR 0002

Two of these — the timezone and the file paths — are the same bug in different clothing: behaviour that depends on the machine it runs on. The host's timezone in one case, the working directory in the other. Both produce output that changes depending on who runs it, and neither announces itself.

07

How it gets scheduled and checked

The pipeline can be run by hand, one command at a time. It can also be run as a single scheduled job, which is what Airflow is for. The interesting detail is how much detail the scheduler can see.

Why the schedule is set to "never"

Airflow's usual job is to run things on a timetable. Here it is deliberately set to manual-trigger-only, because the source is a static archive file that does not change. A nightly schedule would re-read identical bytes every morning and present that as a working pipeline. It runs when a new archive is downloaded — which is the real cadence.

What CI checks, and the trick that makes it possible

The dbt models cannot run without bronze tables, and bronze tables come from a 191 MB archive that is far too large to keep in the repository. The obvious workaround — committing a small pre-built table — was rejected, because it would be a generated file that nothing regenerates, free to drift away from what the ingestion code actually produces, with no test able to notice.

Instead, CI runs the real ingestion against the five-row fixtures, then points dbt at the result. Nothing generated is stored, and every model and every dbt test runs on every change. The full run takes 2 minutes 18 seconds.

A useful accident: the posts fixture mentions two author IDs that the users fixture does not contain. So CI produces rows with author_status = 'unresolved' — a case the real archive never produces, since its user list is complete. The tiny test dataset covers a code path the full dataset cannot reach.

Deliberately out of scope — not oversights

Databricks

The commercial cloud platform this was originally prototyped on. Dropped as a requirement because a project that needs cloud credentials is a project nobody can run — including a reviewer. dbt makes it a swap of one adapter, not a rewrite, so it can return when there is a reason to pay for it.

An AI enrichment layer

Classifying post topics with a language model is a natural fit, and the existing tags give free ground truth to score against. Deferred because doing it properly means solving repeatability, caching, a cost ceiling and an accuracy evaluation — a project in itself. A version without those would be worse than not building it.

Containers, streaming, Kubernetes

The Dockerfile was deleted rather than fixed, because it did not work and nothing would have told you so; it returns only alongside a CI job that builds it. Streaming is out because the source is a static file — streaming it would be theatre.

Running it yourself

Four commands, after downloading the archive. No account, no credentials, no services to start. 

# install, and make the project's code importable
uv sync --group dbt
uv pip install -e . --no-deps

# stage 1 — read the XML into bronze tables (Spark)
python pipelines/bronze_posts.py     # 26,764 rows
python pipelines/bronze_users.py     # 71,811 rows

# stage 2 — build silver and gold, and test them (dbt)
dbt build --project-dir dbt --profiles-dir dbt

# checks
pytest                               # 65 tests, ~2 min
ruff check .                         # lint

To run the whole thing as one scheduled job instead, install the extra orchestration dependencies and trigger the DAG: 

uv sync --group dbt --group orchestration
airflow dags test lakehouse          # 12 tasks, ~4 min

And to reproduce exactly what CI does — which needs no data download at all, because it runs on the committed fixtures: 

DATAFLOW_CONFIG=configs/pipeline.ci.yaml python pipelines/bronze_posts.py
DATAFLOW_CONFIG=configs/pipeline.ci.yaml python pipelines/bronze_users.py
dbt build --project-dir dbt --profiles-dir dbt --vars "{...fixture paths...}"
11

The idea underneath all of it

If there is one thread running through this project, it is a suspicion of things that look fine.

Every bug described in this report shared a shape: nothing failed. Timestamps were wrong but present. The join lost a column but returned the right number of rows. The scheduled run went entirely green and wrote nothing. Config files described a data source that had never existed. In each case the system reported success, and a person had to notice.

So the defences are built around that: row-count baselines that a refactor cannot quietly change; tests that pin properties the current data does not even exercise; a rule that any file nothing checks gets deleted rather than kept "for later"; written decision records so the reasoning outlives the memory of it; and CI running the real pipeline on a clean machine that shares none of the author's assumptions.

None of that is exotic. It is just the recognition that in data work, the failure that costs you is rarely the one that crashes.
